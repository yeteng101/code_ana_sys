17 条资源操作和 32 条同步关系的 recall 为 0，因为目前分析器未输出这两类事实。

调用链样本是既有图的回归标注，本轮无样本内误报、遗漏，不能据此声称图中

unconfirmed，严格 confirmed-only recall 为 0；这表示确认数据缺失，而非全部边错误。

## 79.37% 的边界

看板与 README 记录 requested_edges=1459、confirmed_edges=1158，1158/1459=79.3694%。
现在发布的图为 633 节点、1481 边：1352 direct_call + 129 callback_edge。
历史分母少 22 条，与报告阶段增加异步/回调边的处理相容，但缺少该次完整阶段产物，
无法逐边证明差集。保留历史统计，不能把 1158 除以 1481 冒充原来的覆盖率，
也不能把 coverage_rate 当作本次 precision/recall。

## 优先复核的误差类型

1. **函数指针和回调**：129 条 callback_edge 的 confidence < 0.8。
   它们应保留候选状态；缺少唯一目标/注册来源不能升级为 confirmed。
   回调注册与触发边要分别取证，不能把异步发送端误标成直接调用用户回调。
2. **宏与条件编译**：发布图的 condition 均为空，且来源为 macOS 配置。
   宏展开中的调用点可能是 `POST;` 等源码片段。证据片段存在不等于在所有
   平台配置均可达；Linux epoll 与 macOS kqueue 不能混作一个运行配置。
3. **跨线程边**：调用图不证明 happens-before。新同步集包括条件变量虚假唤醒、
   relaxed 读取、合并通知和可并发回调等反例，但没有同步分析器原生预测。
   32 条同步 FN 是能力缺口，不能靠导出标准答案“修复”。
4. **资源生命周期**：17 条真实 libuv 操作未检出；本轮只评价操作事实，
   不将泄漏标签直接作为外部 API 结论，也不把未找到释放直接当作泄漏已确认。

当前图引用的证据文件/行号/片段均与固定源码匹配（见 `graph-audit.json`）。
这仅证明证据锚点完整性，不证明推导关系、目标解析和时序假设正确。

资源与同步原生提取，再比较候选召回和确认精度。人工复核尚未完成。
