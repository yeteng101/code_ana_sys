### 4. 低命中率原因

libuv baseline 中资源流和同步关系 recall 为 0，但这不是“分析器没有输出”：

```text
libuv 资源流：256 项预测、348 条证据
libuv 同步关系：32 项预测、61 条证据
Redis 资源流：263 项预测、264 条证据
Redis 同步关系：0 项预测
```

评测器按精确 identity 匹配。资源流的预测 identity 是：

```text
[resource, function, file, line, kind]
```

Gold 中的 resource 是稳定语义 ID，例如 `rf_libuv_fs_fd_v1`；当前 v1 分析器把
调用点变量名当作 resource，例如 `watchers`、`sockfd`。两者字符串不一致，因此
即使函数、文件、行号相同，也会被判为 `unlabelled_predictions` 或 FN。

资源流 0% 还来自另外三个原因：

```text
1. Gold 区分 acquire/transfer/release，当前分析器只输出 acquire/release。
2. 部分 Gold 调用点在 graph.json 中不存在，例如 async.c 的 306、313 行。
3. Gold 混入了 generated_candidate/pending_review 的重复资源候选。
```

以 libuv 资源流为例：

```text
当前 Gold：62 条
其中待复核候选：35 条
已复核真实操作：17 条
忽略 resource ID，只按函数、文件、行号、kind 匹配：5 / 17
```

所以资源流的修改目标是同时解决“身份 ID 对齐”和“输入图/规则覆盖不足”，不是单纯
把标注从 Gold 中删掉。

同步关系 0% 的原因不同。当前分析器主要提取同函数 lock 到 unlock、相同 condition
对象的 signal 到 wait。Gold 需要的是跨函数的线程通信事实，例如：

```text
post 解锁共享队列
worker 获取同一队列并消费
```

当前预测和 Gold 的端点函数、位置、condition 均不匹配。即使忽略 condition，
libuv 的端点位置匹配仍是 0 / 32。Redis 当前没有命中任何同步规则，因此 22 条
同步 Gold 全部为 FN。

### 5. 修改方案

#### P0：清理待复核候选

`scripts/prepare_validation_truth.py` 生成 libuv 资源流 Gold 时，应跳过
`generated_candidate` 或 `pending_review` 的 resource，避免重复候选人为扩大 FN
分母。这一步不能让 recall 自动上升，但能让 baseline 反映真实 Gold。

#### P0：统一资源身份 ID

在 `clang_pipeline/resource_flow.py` 中增加稳定的 API 到 resource ID 映射：

```text
uv__fs_open / uv_fs_open / uv__fs_close -> rf_libuv_fs_fd_v1
uv__getpwuid_r                          -> rf_libuv_getpwuid_buf_v1
uv__async_start / uv__async_stop        -> rf_libuv_async_fd_v1
uv__getaddrinfo_work / uv_freeaddrinfo  -> rf_libuv_getaddrinfo_v1
uv__fs_scandir / uv__fs_scandir_cleanup -> rf_libuv_scandir_entries_v1
uv_dlopen / uv_dlclose                  -> rf_libuv_dlopen_handle_v1
```

预测中应同时保留：

```text
resource：统一稳定 ID
resource_expression：调用点变量或参数表达式
```

`resource` 参与评测，`resource_expression` 只用于解释和人工复核。

#### P1：补 operation 类型与资源规则

资源流 v2 需要：

```text
增加 transfer 识别
增加 uv__make_pipe、uv__open_cloexec、uv__getaddrinfo_work、
uv_freeaddrinfo、uv__fs_scandir、scandir、dlopen、dlclose 等规则
重建缺失的 Clang 调用边，尤其是 async 和跨函数所有权边
```

#### P1：重做同步关系提取

同步关系 v2 应从“同函数 lock 配对”扩展为：

```text
同一 mutex 的 unlock 到后续 lock
共享队列 insert/head 等支持证据
thread_create 到 worker 入口
condition signal 到 wait
held_locks 上下文跟踪
```

这样才能输出 Gold 所要求的跨线程 `happens_before` 事实。

#### P1：增加身份差异诊断

正式评分前先统计：

```text
仅 resource ID 不同，但函数、文件、行号、kind 相同
仅 condition 不同，但同步端点位置相同
```

这两类计数能把“身份未对齐”和“分析器没有提取”分开，避免继续把大量真实输出笼统
记作 recall=0。

### 2. 同步关系分析器

当前提取：

```text
mutex_lock
rwlock
condition_variable
event_wait
event_notify
thread_join
```

libuv 运行结果：

```text
status: succeeded
items: 32
evidence: 61
```

Redis 运行结果：

```text
status: not_available
items: 0
evidence: 0
```

当前同步规则没有在 Redis 图上命中关系，因此 Redis 同步关系仍为 0 条预测，
baseline 中记录 0 TP / 0 FP / 22 FN。

同一函数、同一资源 key 的 lock → unlock 作为较高置信度的事实；
跨线程通知/等待和 event 关系使用较低置信度，并保留 `unknown`，不直接输出
`deadlock` 或 `race`。
